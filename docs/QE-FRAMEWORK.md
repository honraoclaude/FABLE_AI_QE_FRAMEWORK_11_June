1. Overview & Philosophy

Core Philosophy
Quality Engineering is everyone's responsibility — starting at requirements, not after code is written.
Bugs caught earlier cost 10–100x less to fix. This framework embeds quality at every stage of the
software delivery lifecycle through automation, AI-assisted analysis, and clear accountability.

1.1 Framework Goals
Shift quality left — catch defects at requirements and design, not in production
Automate intelligently — right test at the right layer
Make quality visible — risk, coverage, and confidence surfaced in real time
Continuous improvement — the framework learns and adapts every sprint

2. Definition of Ready (DoR)

The DoR is the gate that must be passed before a story is eligible for a 3 Amigos session. It is checked twice: at backlog refinement and again immediately before scheduling the session.

2.1 When DoR Is Checked
Gate 1 — Backlog Refinement: AI runs initial check, gaps auto-assigned
Gate 2 — Pre-3 Amigos: AI re-checks, QE Lead gives final human sign-off

2.2 Global Baseline (All Stories)
Story title is clear and unambiguous
Business value / 'why' is stated
Story is independently deliverable
Story is estimable by the team
Story fits within one sprint
Acceptance criteria drafted (even rough)
Priority assigned by PO
Dependencies identified or stated as none

4. Definition of Done (DoD)

Every story gets a tailored DoD generated by AI during the 3 Amigos session and refined by the team. Both Dev (self-certification) and QE (independent verification) must sign off before a story moves to Ready for Release.

4.1 Global Baseline (All Stories)
Code reviewed and approved (min 1 peer reviewer)
All AC scenarios passing
No critical or high severity bugs open
Unit tests written and passing
Relevant documentation updated
Feature flag configured (if applicable)
Deployed to staging environment
QE sign-off received

4.2 Story-Type Extensions
Feature Stories
All Gherkin AC scenarios passing
UI Automation tests written for automation candidates
API tests written for API automation candidates
Accessibility check passed (WCAG 2.1 AA)
Performance budget not exceeded
Cross-browser tested (defined browser matrix)
Risk Register updated for new risks introduced
Regression pack updated with new regression scenarios
PO demo completed and signed off

Bug Fixes
Root cause documented in Jira
Fix verified against original defect steps
Regression test written to prevent recurrence
Related areas smoke tested (defect density check)
Defect Density Index updated for affected module
Previously Failed Test Register updated
No new defects introduced in fix

Tech Debt
Technical approach documented
No regression in existing functionality
Performance benchmarks maintained or improved
Code coverage maintained or improved
Architecture decision record (ADR) updated if applicable
Risk Register updated if debt introduced new risk

4.3 Dual Verification Process
Stage 1 — Dev Self-Certification: Dev checks off all Dev-owned items before raising a PR. Cannot submit for QE review until all Dev items are complete.

Stage 2 — QE Independent Verification: QA independently verifies all items. QA cannot simply accept Dev's word — each item must be verified. Any failed item blocks the story from reaching Ready for Release.

5. Acceptance Criteria Generation & Categorisation

5.1 AC Generation Process
Triggered when QE marks 3 Amigos as complete
AI generates Gherkin (Given/When/Then) scenarios from story content
Minimum output: one happy path, one negative path, one per edge case
Security AC auto-added for stories touching auth, payments, or personal data
Accessibility AC auto-added for all UI stories
QA reviews, edits, and approves in portal before AC is written to Jira

5.2 AC Test Type Categorisation
Test Type
AI Assigns When...
Unit
Scenario tests a single function, calculation, or validation rule in isolation
Functional
Scenario tests a feature behaviour end-to-end within one layer (UI or API)
E2E
Scenario spans multiple systems, services, or user journeys
Regression
Scenario covers existing behaviour that must not break — flagged on re-work stories
API Automation
Scenario can be fully validated at the API layer without UI interaction
UI Automation
Scenario requires browser interaction to validate

5.3 Automation Candidate Scoring
AI flags each scenario as an automation candidate based on:
Repeatability — run on every build? Strong candidate
Stability — relies on static data/UI? Strong candidate
Complexity — too many variables or manual judgement? Manual
Frequency — high regression risk? Strong candidate
Layer — API-testable without UI? API automation preferred

QA confirms or overrides AI automation candidate flag before approving AC.

7. Risk-Based Regression Testing

For every release, AI analyses the risk register, changed stories, defect density, and previously failed tests to automatically build a tiered regression pack.

7.1 AI Selection Signals

Previously failed test history
AC scenarios tagged as Regression

7.2 Defect Density Index (DDI)
DDI = (Total defects × severity weight) ÷ stories delivered in that area

7.3 Tiered Execution Strategy
P1 — Smoke (Always runs, every release)
Core user journeys that must work no matter what
Fully automated, runs in CI on every deployment
Target: < 10 minutes execution time
Failure = release blocked immediately

P2 — Risk-Based (Scoped by risk signals)
AI selects based on risk score ≥ 6, areas touched, bug history, regression-tagged AC
Mixed: automated where available, manual/exploratory for gaps
Target: < 2 hours execution time
Failure = release blocked pending triage

P3 — Full Regression (Pre-major release or quarterly)
Complete test suite across all product areas
Triggered before major releases, quarterly, or manually by QE Lead
Full automated suite plus exploratory charters
Failure = risk assessed before go/no-go decision

12. Environment & Release Management

12.1 Environment Health Check
Portal checks environment readiness automatically before any regression run. Services, data, and feature flags are all verified before testing begins.

12.2 Feature Flag Management
Each story with a feature flag has environments tracked in portal
Rollback plan defined: toggle OFF instantly if critical bug found
Cleanup date set per flag to prevent flag accumulation

12.3 Rollback Criteria
Automatic Rollback Triggers
Error rate increases > 2% post-deploy
P1 smoke tests fail in production monitoring
Payment success rate drops > 1%

Manual Rollback Decision Triggers
High severity bug reported by users
Performance degradation > 20%

Rollback owner: Release Manager | SLA: < 15 minutes | Rollback must be tested in staging before release.

13. Exploratory Testing Charter Library

A reusable library of exploratory testing charters organised by product area. Charters evolve based on bugs found, and findings feed back into AC edge cases and the Risk Register.

13.1 Charter Structure
Mission — what are we exploring and why
Area — product module and linked risk
Starting points — specific scenarios to begin exploration
Time box — fixed duration (typically 30–90 minutes)
Tester — assigned QA

13.2 Charter Feedback Loop
Bugs found → logged in Jira
Charter updated with new starting points
New edge cases → added to AC template for similar stories
Recurring findings → new Risk Register entry created

13.3 Charter Library Organisation
Payments: happy paths, edge cases, error states, security
Auth: login flows, session management, MFA
Checkout: discount logic, cart behaviour, pricing
Each charter versioned and timestamped

15. Continuous Improvement

15.1 Monthly Retrospective (Portal Auto-Generates)
What escaped to production and which area
What was over-tested (low DDI, no bugs in 6+ sprints)
Automation ROI — which tests caught real bugs vs never triggered
Recurring DoR/DoD gaps — criteria that keep being skipped

15.2 Quarterly Framework Review
DoR criteria still relevant?
DoD criteria appropriate per story type?
Risk scoring weights calibrated to actual outcomes?
Automation framework still fit for purpose?
Charter library up to date?
Regression suite healthy (flaky tests < 2%)?

15.3 AI Model Recalibration
After every release, the AI scoring model is recalibrated based on actual outcomes. If a module was under-predicted as high risk and produced production bugs, its weight is adjusted automatically. QE Lead reviews recalibration recommendations quarterly.
